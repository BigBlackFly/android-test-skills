> 本文档只做**缺口分析 + 计划**，**不构成任何变更授权**。
> 涉及 `framework/`、`SKILL.md`、`docs/` 的改动，实施前必须先出
> 「原文 vs 修改后」提案经人确认。
> 工作量标注：S < 半天，M = 1-2 天，L > 2 天。

## 零、协作准则（本次教训，最高优先级）

**不知道或者无法做决定的，应该问人，而不是自作主张。**

本次 178 实战中，AI 在 17:05 已拿到「31 PASS / 0 FAIL」的确定结论
（仅剩一个环境类假 WARN），却未停下汇报，自行连改 4 版代码、多跑 4 次
全流程（约 22 分钟纯浪费），最终仍未修好，靠事后追问才定位到是「框架基线
与平板方向语义不匹配」—— **这本是应当上报给人决策的事**。

**行为准则（立即生效）**

| 场景 | 正确做法 |
|---|---|
| 测试结论已确定（PASS/FAIL 不再变），剩余仅为环境噪音 | **先汇报，由人决定是否处理**，不自行连试多版 |
| 发现疑似框架层问题（非用例脚本问题） | **上报**，不自行修改框架 |
| 分层归属有争议（该进 framework 还是 `_flow.py`） | **问人**，不自行推断 |
| 同一问题改法 ≥2 种且各有取舍 | **列选项问人**，不自行选定 |
| 要做超出当前任务范围的改进 | **先提案**，不"顺手做了" |

**判据**：连续 2 次以上的"尝试性修改 + 全流程验证"未收敛 → 立即停下问人。

## 二、用户提出的核心诉求

1. **遍历（探索）应有记忆与导航能力**
   - 读已有 case + 知识卡 → 知道**哪些路径已探明、哪些是盲区**
   - 据此**自主做页面导航探索**
   - 本地保留 dump + 截图，供后面写代码时参考

2. **执行期动态数据必须真实调用，禁用缓存**
   - OCR、视觉在**执行时现场真跑**
   - **不得**使用探索期 dump 期间缓存的数据 —— 换设备/换方向即失效

3. **知识卡不应包含任何设备特殊信息**
   - 只写 App 事实（控件 rid、页面路径、Canvas 特性、因果类坑）
   - 不写坐标、横竖屏、样本值、机型/版本标注

4. **核心目标**：做一个**聪明的 skill**（当前"还远远达不到"）

## 三、缺口分析

### 缺口 1：统一执行模型缺失（因果位置：**最根本**）

**现象**：一个用例被拆成三段互不相通的东西——

```
① 探索期（agent 临时脚本）  →  ② 知识卡（自然语言）  →  ③ 执行期（用例脚本）
   _probe_*.py / probe_page      写"点 (123,203)"        抄成硬编码
```

**问题**：探索期是**临时代码**（用完即删），知识卡把结论写成**自然语言**，
执行期再**人工翻译**回代码——**三段之间没有任何自动通道**。

=> 探索成果无法自动复用，且每次翻译都会引入漂移（本次 178 的
`_col_x(t)=w//2` 就是执行期凭空新造的"近似值"，与探索无关）。

**这是"越做越复杂"的根源**：每换一个 App/页面，都要重走一遍三段式。

### 缺口 2：遍历没有"记忆"，也没有"地图"

| 诉求 | 现状 | 证据 |
|---|---|---|
| 判断路径已知/未知 | ❌ **完全没有** | 工作流第 2 步靠**人/AI 读文档判断**，无覆盖度机制 |
| 自主导航探索 | ⚠️ 半成品 | `probe_page(label)` 只探**当前页**；`goto_*` 是**手写固定链路** |
| 保留 dump+截图 | ⚠️ 有但未启用 | `probes/`、`traces/` 存在，但 `traces/` "从未被启用过" |

**关键缺失**：探查产物是**散落文件夹**（`probes/<包名>/<label>/`），
不是**可查询的图** —— 不知道"A 页 → 点 X → B 页"这条边是否探过，
不知道哪些页面还没去过。**探索结果不可累积**。

### 缺口 3：执行期与探索期无硬边界（用户诉求 2）

| 层 | 探索期 | 执行期 | 问题 |
|---|---|---|---|
| UI 树 | `probe_page`（缓存 dump） | `el_bounds`（实时） | 实时 ✅ |
| **OCR** | `cached_ocr`（**默认吃缓存**） | `ocr()`（实时） | ⚠️ 执行期若调 `cached_ocr` 读旧设备数据 |
| 视觉 | 无探索期概念 | `vision_ask`（实时） | ✅ |
| 坐标 | dump 里"看出来" | **抄成常量** | ❌ **脆弱源** |

**结论**：缓存**只应服务于"写代码时参考"**，**绝不能进入执行路径**。
框架目前**没有这条边界约束**。

### 缺口 4：无运行时标定能力（用户诉求 3 的成因）

- 规范要求"坐标不写死、运行时现场标定"（`docs/case-writing.md` 明文）
- **但框架零支持** → 各用例自行实现（179 `calibrate_picker`、178 `_col_x`），
  重复造轮子且质量参差
- 知识卡因此只能记"实测值"当线索，**再告诫"要现场校准"** —— 而告诫不可执行

**结论**：**知识卡里之所以要写设备信息，是因为框架没有能力自己算出来。**
清理知识卡（诉求 3）与补标定能力（缺口 4）是同一件事的两面。

### 缺口 4.5：导航路径不成体系（用户新提议，2026-09-11）

**现象**：导航链路以两种形态散落 ——

- `_flow.py` 里的 `goto_*` 函数（**已具雏形**：`goto_课程表空状态`、
  `goto_图库导入_基本信息确认页`、`goto_手动创建课程表`）
- 用例脚本里**手写的裸 `tap_*` 序列**（如 178 前置自己拼链路）

**问题**（以 178 实战为证）：

1. **每个 case 各自拼链路**，同一条边被重复实现 → 改动要改 N 处
2. **方法隐藏前置假设**：`goto_手动创建课程表(t)` 内部假定"当前在空状态"，
   不满足时直接 `blocked("课程表非未添加课程表")`（178 首跑因此 BLOCKED）。
   **它能检测失败，但不能自愈，也不告知调用方前提是什么。**
3. **同目标多条边时无信息可供选择**：知识卡记着"列表页 BACK 一次到周视图"
   比"主页→更多→课程表"便宜，但这条经验**只存在于自然语言里**，
   AI 无法据此自动选最优。

**用户提议（定案方向）**：**把导航路径做成方法 —— 一个方法 = 一条点击边**
（A 页面 → 点 X → B 页面），case 只组合这些方法 + 写断言。

**为什么这个方向是对的**：

| 收益 | 说明 |
|---|---|
| 脆弱性收敛到一处 | 路径一变只改一个方法，而非各 case |
| case 变薄 | case 只表达"验证什么"，符合 SKILL"用例只写断言" |
| 可组合 | 长路径 = 短路径串联（`goto_手动创建课程表` 已内部调 `goto_课程表空状态`）|
| **与遍历天然对齐** | 遍历就是在发现边；**每探明一条边就固化成一个方法** → 探索产出物 = 路径方法集合（直接服务缺口 2 / 用户诉求 1）|
| 失败可定位 | 哪条边断了清清楚楚，不像"前置 BLOCKED"那样含糊 |

**分层归属（关键，勿越界）**：

| 层 | 内容 | 归属 |
|---|---|---|
| 路径**本身**（"进课程表模块"、"拍照导入链路"） | **App 特有** | `cases/<包名>/_flow.py` |
| 路径的**组织/调用/查询机制**（自动挂载、组合、元信息检索） | 通用 | `framework/`（需批准，且待第二个 App 出现再上提）|

> 注："每个 App 的操作路径都一样"**不成立** —— 通用的是"路径该怎么被
> 组织与调用"这个机制，路径内容本身是 App 特有的。与 `learn_dialog`
> 那次是同一类判断。

### 缺口 5：SKILL 是"文档驱动"而非"能力驱动"

| 现状（文档驱动） | 应然（能力驱动） |
|---|---|
| 卡写"点 (123,203) 返回" | 框架能**自己找**返回按钮（desc/rid） |
| 卡写"用 `t.ocr(1350,1870)` 补读" | 框架能**自己算**该读哪块（从弹框 bounds 推） |
| 规范说"运行时标定"，无工具 | **有标定工具**，调用即生效 |
| AI 靠"读卡 + 记忆 + 猜"定位 | AI 靠**可执行能力**定位 |

**这是"不够聪明"的真正原因**：大量**本该是代码的事**被写成了**文档里的告诫**。

### 缺口 6：方向语义错位（`lock_portrait`）

- `lock_portrait()` 硬设 `accelerometer_rotation=0` + `user_rotation=0`
- 在 TB323FU 平板（自然方向横屏）上，`user_rotation=0` 得到**横屏**，
  与"锁竖屏"的名字**相反**
- 且 App 冷启动会把 `accelerometer_rotation` 改回 1 → finish 时基线(0)≠现状(1)
  → 报「污染设备环境」（**漂移真实存在，框架报得没错**）

**注**：此为 `plan/roadmap-to-A+.md` 已评审定案的设计（"两次取基线"，
rotation 两键纳入默认监控）。**不建议改为 ignore**——那会破坏
"中途意外转屏能被捕获"的监控能力。应解决的是**来源**（冷启动顶掉锁定）。

### 缺口 7：无续跑能力（时间放大器）

改一行也要跑全流程：冷启动 `pm_clear` + 重建前置约 100s。
本次后 4 次运行的**前置纯重复**。

## 四、改进计划

> **顺序原则**：先小后大，每步可独立验证、可独立叫停。
> **风险提示**：缺口 4 / 5 / 6 的落地会触及**已有 15 个用例的回归**。

### 阶段〇：协作准则落地 【S】—— 应最先做

**做什么**：把「零、协作准则」写入 `SKILL.md` 的变更管控章节旁，
作为 AI 行为约束。

**理由**：本次 22 分钟浪费的直接原因就是缺这条。**零技术风险，收益立竿见影。**

**验收**：`SKILL.md` 含该准则；下一次实战中，AI 在结论确定后主动停下汇报。

### 阶段一：执行期硬边界 【S-M】—— 直接命中用户诉求 2

**做什么**
1. `cached_ocr` / `cached_dump` 明确标注为**仅供探索期与写代码参考**；
   执行路径（用例 `run()`）中禁止调用。
2. 增加**护栏**：`TestCase` 记录"是否处于执行期"，执行期调用 `cached_*`
   时记 WARN 或直接拒绝。
3. `docs/case-writing.md` 写明该边界。

**验收**
- [ ] 单测：执行期调用 `cached_ocr` → 触发护栏告警。
- [ ] 文档：`case-writing.md` 有"缓存不得进入执行路径"条目。

**影响面**：小。现有 15 个用例是否已违规需先扫描确认。

### 阶段二：运行时标定能力 【M-L】—— 直接命中用户诉求 3 的成因

**做什么**（分层！见下）

**第一步：App 专属（`cases/com.zui.calendar/_flow.py`，自由迭代，无需批准）**

```python
def win_size(t):          # 当次窗口尺寸（不用 wm size —— 实测不可信）
def dialog_panel(t):      # 弹框内容区 bounds（不写死坐标）

def read_wheel_value(t):  # 由标定结果定位并读值
def scroll_until(t, cond, max_screens=6):  # 反复滑动直到条件成立
```
- 合并 179 的 `calibrate_picker` 与 178 的 `_col_x` 思路，**只留一份**
- 改后 178 里所有 `w//2`、固定比例滑动、固定次数滚动**全部替换为实测**

**第二步：通用骨架（`framework/`，需人批准，先出提案）**

**验收**

- [ ] **换方向验证**：同一脚本在横/竖屏下均能跑通（关键验收项）。

### 阶段二点五：导航路径方法化 【M】—— 直接命中用户新提议（缺口 4.5）

> **定位**：本阶段是**用户新提议的落地方案**，与阶段一/三同为"低风险高收益"，建议**排在阶段二（运行时标定）之前或并行**——因为路径方法内部会用到标定，但路径方法本身的骨架不依赖标定。

#### 核心定义（用户定案）

**一个路径方法 = 一条点击边 = "从 A 页面 → 点 X → 到 B 页面"**

不是"一个页面一个方法"，而是**按一条完整导航路径切**。

```python
goto_课程表空状态(t)        # 主页 → 更多 → 课程表
goto_手动创建课程表(t)      # 课程表空状态 → 手动创建
```

#### 四条约定（前三条经用户确认，第四条待样板验证）

**约定 1：每条路径方法自带「前置状态检查」** ✅ 用户确认

> 用户理由原文：「如果条件满足的话可以省 clear app 冷启动要重新创建前置条件的时间开销」

```python
def goto_课程时间设置页(t):
    if _on_activity(t, "TimeSlotSettings"):     # 已在目标页 → 直接成功
        return True
    if _on_activity(t, "EditTimetableActivity"):  # 已在上一跳 → 只走最后一跳
        return _tap_设置入口(t)
    # 否则才走完整前置（可能含 pm_clear / 冷启动）
```

**收益量化（本次实战数据）**：178 单次 320s 中**前置冷启动约 100s**
（`pm_clear` + 重建课表 + 过 3 个首启弹框）。9 次运行中**后 4 次前置完全重复**。
前置检查可让"改一行断言"的调试不再重付这 100s。

**已有先例**：`goto_图库导入_基本信息确认页(t, skip_if_ready=True)`
（`_flow.py` L334）就是这个思路，只是**未普及**。

**约定 2：同一目标多条边 → 拆成多个方法，并给 AI 足够信息选最优** ✅ 用户确认

> 用户理由原文：「拆成多个方法。但同时要给 AI 足够的信息知道最优的是哪个」

```python
def goto_周视图__从列表页(t):
    """[从] 全部课程表列表页 TimetableListActivity
       [到] 周视图 TimetableActivity
       [成本] 1 步   [实测] 最快
       [前提] 当前已在列表页
       [备注] 这是列表页→周视图最便宜的边（知识卡实测 2026-09-10）"""

def goto_周视图__从主页(t):
    """[从] 日历主页 AllInOneActivity
       [到] 周视图 TimetableActivity
       [成本] 3 步 + 冷启动风险  [实测] 较慢
       [前提] 需先过首启弹框链
       [备注] 任何时刻可用，但有弹框链风险"""
```

**关键**：元信息必须**机器可读**，不能只是自然语言——否则又回到"读文档靠猜"。
- **方案 A（本次采用，零框架改动）**：固定 docstring 格式
  （`[从]/[到]/[成本]/[前提]/[备注]`），AI 读代码时可解析
- **方案 B（暂不做）**：结构化元数据注册 + `t.flow.routes(from=X, to=Y)` 查询接口，
  留到第二个 App 出现、需要跨 App 复用时再上提框架

**约定 3：命名采用「起点→终点 + 业务别名」** ⚠️ 待样板验证后定案

| 方案 | 优点 | 缺点 |
|---|---|---|
| 纯「意图」（现状 `goto_课程表空状态`） | 好读 | **隐藏前置假设** —— 正是 178 踩的坑 |
| 纯「起点→终点」 | 前提透明 | 冗长；起点叫法不统一 |
| **混合（推荐）** | 兼得 | 稍长 |

**推荐形态**：`goto_<意图>__从<起点>(t)`，如
`goto_课程表空状态__从主页(t)`、`goto_周视图__从列表页(t)`

**理由**：把**起点写进函数名**，AI 一眼可知"这方法假设我在主页"，
避免 178 那种误用；同时保留意图部分保证可读性。

> ⚠️ **命名是长期约定，改动成本高**（要动所有 case）。
> **定案方式**：先按混合式写 2-3 个方法当样板 → 在真实代码上评估 →
> **由人拍板后**写入 SKILL 规范。

**约定 4：是否需要「case 禁止裸 tap_* 导航」的硬约束** ❓ **待用户决定**

