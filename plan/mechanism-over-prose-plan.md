## 〇、总纲：一条主线判断

> **能力可以交给 Agent，纪律和证据不能。**
>
> 判据：这条规则违反时，能否从产物（报告 / DB / 截图 / 退出码）里**机器检测**出来？
> - 能 → 机制管（run_case / eval / lint），与模型强弱无关
> - 不能，属于判断质量 → 交给 Agent，模型升级自动受益

推论：现有 SKILL.md 是"弱模型时代的防御工事"，目标形态是
**薄规则（告诉 Agent 去哪）+ 厚机制（证据 / 守门 / eval，证明它真的到了）**。

## 一、减负：把"判断"还给 Agent，把"守门"留给机制

### 1.1 可以交给 Agent 的（规则瘦身清单）

| 现在的负担 | 处置 |

### 1.2 必须留在机制里的（不可下放）

### 1.3 前提条件：先建 eval 再减负

## 二、可移植性：换设备差不是 case 写得不好，是框架没把"设备无关表达"做成默认路径

### 2.1 失败归因四类（先审计再优化）

| 失败模式 | 根源 |
|---|---|
| 坐标 / 偏移失效 | 屏幕尺寸、DPI、圆角 / 挖孔不同 |
| 元素不在首屏 | 小屏 / 换形态后布局折叠、控件进 overflow |
| 时序失败 | 慢设备渲染慢，固定 sleep / 短超时 |
| 断言失效 | 文字断言撞 ROM 字体 / 语言 / OCR 识别率 |

一次性动作：同 case 两台设备跑，diff 失败步骤并归类，拿数据定优先级。

### 2.2 框架 API 盘点与新增（治本，全部通用、符合分层边界）

> **现状核对（2026-09-16）**：wait_rid / wait_text / wait_activity 已实现
> （test_framework.py:1372/1386/1399），实施者**不要重复实现**。清单分三类：

| 类别 | API | 现状 | 说明 |
|---|---|---|---|
| **已有，无需改动** | `t.wait_rid(rid, timeout, interval)` | ✅ :1372 | P1 的 _flow.py 改造直接消费它 |
| **已有，无需改动** | `t.wait_text(text, timeout, interval)` | ✅ :1386 | 同上 |
| **已有，无需改动** | `t.wait_activity(substr, timeout, interval)` | ✅ :1399 | 计划初稿遗漏，一并纳入 _flow.py 改造 |
| **需新增** | `t.wait_gone(target, timeout)` | ❌ | 删除类断言（"课程已消失"）的另一半 |
| **需新增** | `t.scroll_to_rid(rid, timeout)` | ❌ | 循环 swipe+dump 直到命中或出屏兜底 |
| **需新增** | `t.ocr(below=rid, above=rid)` / `region_of(rid)` | ❌ | 运行时区域派生（见 §三） |
| **需评估，押后** | `t.tap_in(el, anchor=)` / `tap_right_of()` | ⚠️ | 与 `tap(rid=)`（_tap_unified:992，轮询定位+点中心）语义重叠；现有用例无"点元素非中心"的真实需求，**按 SKILL.md「升级路径」约定，等第二个 App 证明需要再做** |

```python
# P1 新增后的目标用法（仅列新增项）：
t.wait_gone(DLG_TITLE)                    # 删除类断言
t.scroll_to_rid(ET_TEACHER)               # 小屏布局折叠
t.ocr(below=HEADER_RID, above=NAV_RID)    # OCR 区域运行时派生
t.ocr(region=t.region_of(RID_LIST))
```

**UI settled 检测：押后，拆独立 plan。** 原因：dump 全文一致性比较代价高（~300KB/次），
"稳定"定义（节点计数？bounds 不变？Activity 不变？）各有误判风险；
accessibility 事件静默需要自注册 AccessibilityService + 桥接，是独立大功能不是"配套能力"。
**当前兜底**：`wait_rid` + 短 `time.sleep`（可 lint 豁免），待 wait_* 普及后按记分卡数据决定是否立项。

### 2.3 lint 新增可移植性检查

- 手写轮询检测：`while time.time() < deadline` + `sleep` → 提示改用 `t.wait_*`
- 偏移溯源：`bounds[i] ± 字面量` 升级——同行无 `# calibrated: <机型>` 戳即 ERROR

### 2.4 定位失效三归因（写进 case-writing 一句话版）

同 APK 跨设备 rid 相同（编译进 APK），rid 找不到时按序归因：
1. **没等到**（异步渲染，dump 太早）→ `wait_rid`
2. **没滚到**（rid 在树上但 bounds 空 / 出屏）→ `scroll_to_rid`
3. **布局变体**（`sw<N>dp` 切换，rid 真不存在）→ 属 App 本来就不一样，回探查补采

断言建议"rid 断言结构 + text/状态断言语义"双确认，单个 rid 命中不代表内容对。
（厂商 App 特有注意：OTA 频繁 → 版本漂移高发，见 §四；自绘控件无 rid 是 OCR/视觉依赖的根源。）

## 三、OCR / 视觉缓存治理：缓存只许回答"找什么"，不许回答"在哪找"

### 3.1 缓存信息三去向（写进 explore-guide / case-writing 交接语义）

| 缓存内容 | 进 case？ | 形态 |
|---|---|---|
| 事实类：rid 存在、字段名、预期 toast 文案 | ✅ | 作为断言目标，运行时重取后比对 |
| 程序类：到达路径、先滚后点 | ✅ | 流程逻辑 |
| **数值类：y_min/y_max、bounds、热区偏移、OCR 区域** | ❌ **禁止** | 必须转运行时派生表达式；转不出的 → 提案 API，不许硬编码 |

### 3.2 缓存命中前验证 + 降级（对标 Midscene）

> 前置事实：**执行期使用探查缓存已被硬拦截**——v5 A1.4 已落地
> （`_guard_exec_cache` 在 cached_dump / cached_ocr 等入口抛 `ExecutionTimeCacheError`，
> probe_page 免检）。本节与 3.3 是其**进阶增强**：A1.4 管"禁止用"，本节管"怎么把提示用对"。

缓存值可当**提示**，用前运行时验证：先 dump 确认 anchor rid 存在 → 从其 bounds 推区域；
不存在 → 全屏退化。提示错了最多慢一点，不会挂。**查询 / 断言类结果永不缓存**。

### 3.3 交叉比对 lint（精确检测"缓存值回流"，进阶增强）

> 现状：现有 lint 规则 5/6/7（`_PIXEL_PARAMS` 像素参数、模块级像素常量、bounds 固定偏移）
> **已经是"字面量检测"的简化版**——本节是叠加在它之上的进阶，不是从零新建。

- 做法：case 整型字面量 × probes 落盘数值（ocr.json / meta.json / dump.xml bounds）交叉比对
- **两个待基线确定的设计参数**（实施前先跑误报评估）：容差值（±10？±50？DPI 换算？）；
  误报风险（`timeout=60` 撞上某 OCR conf 值一类）——策略：只对**模块级常量与像素参数位**做交叉
  （复用规则 5/6/7 的判据收窄），不做全 AST 字面量扫描，先量化误报率再定 ERROR/HINT 级别

### 3.4 存量迁移

1. 交叉 lint 跑存量用例 → 自动得"缓存回流清单"
2. 逐个替换为 `region_of` / anchor 表达式；替换不了先打 `# calibrated: <机型>` 留痕，进提案队列
3. 双设备 eval 放一个含 OCR/视觉断言的 golden 用例作永久门禁

## 四、版本漂移应对：版本门禁（WARN 级）+ 自愈留痕（细粒度）

### 4.1 版本门禁（1~2 小时，非 AI 参与）

- run_case 启动时 `dumpsys package <pkg>` 取 **versionCode**（不用 versionName，OTA 里可能不动）
- 比对：知识卡头部"验证版本"（**按现行 `_template.md` 格式解析**）+ probes 侧版本戳——
  **前提改动**：`meta.json` 目前无 app_version 字段，需在 `probe_page()` 顺手加一行
  `dumpsys package <pkg> | grep versionCode` 采集
- **失配只打 WARN（"App 已从 X 升到 Y，缓存是 X 时期的"），不废缓存**——门禁的价值不是预测，是挂的时候消灭歧义，把"排查半天"变"一眼归因"
- 小版本升级大多数不动 rid（判断成立），真正的高发破坏是开屏广告 / 升级引导页 / 运营弹窗 / 文案微调——门禁对这些同样有效（都是"版本变了"信号）

### 4.2 自愈链 + 留痕（对标 Healenium）

执行时定位降级链：`rid → desc → text → 视觉`，**硬约束：只允许在同一个 dump 结果内降级**
（当前 dump 里 rid 找不到 → 同一次 dump 里找 desc/text），**禁止跨 dump 重找**——
跨 dump 后页面可能已变化，desc/text/视觉命中的"相似元素"身份保证已断，
报告写"自愈成功"但实际可能点了错误的元素：

- 报告单列「降级事件」，**区分两档语义**：`同 dump 降级命中`（可信度高）/ `视觉兜底命中`（须标记"元素身份未验证"，高危）
- **同一 rid 降级 ≥2 次 → 自动生成知识卡更新提案**（这是比版本比对更精确的 OTA 漂移信号）
- 厂商团队特权：变更结论可直接反馈 App 开发（外部团队做不到的闭环）
- **自愈历史记录（Locator Memory，对标 Healenium）**：降级成功后写 `healing_log.json`（per App）：
  `{rid: "id_save", fallback: "desc=保存", layer: "desc", count: 5, version_code: 83}`。
  下次同一 rid 找不到时先查 healing_log → 命中则**直接走已知降级路径**（省一次 dump + 等待）。
  约束：命中后仍须用**当前 dump 验证** fallback 元素存在且合理（bounds 非空、Activity 对得上），
  验证不通过 → 丢弃该条记录、退回完整降级链（与 §3.2「缓存命中前验证」同原则）。
  版本门禁触发 WARN 时**清除该 App 全部 healing 记录**（rid 可能真变了）。
  报告新增「healing 命中率」指标，累计 count ≥3 的条目自动生成知识卡更新提案

### 4.3 执行时管线（合成业界共识，每步）

```
1. 现采 dump（永远新鲜，学 Mobile-Agent）
2. 缓存/knowledge 的 rid 查找 → 命中后验证签名（text 前缀 / 兄弟元素 / Activity，学 Midscene）
3. 签名不符 → 降级链 desc → text → 视觉（学 Healenium）
4. 自愈 → 报告留痕 + 知识卡提案
5. 断言永远现采现比，不读缓存（学 Midscene「断言永不缓存」；
   check_facts 守"不编造"，本条守"不读过期"）
```

## 六、上下文管理：元数据路由 × 分层渐进式披露

> 两种方法分工：**路由决定"读哪个"，披露决定"读多少"**。渐进式披露（L1 元数据 → L2 SKILL.md → L3 按需资源）已基本落地（docs 子文档、知识卡按节读、场景卡懒加载），缺口在"路由信息散在散文里、不机器可读"。以下三点补齐，全部归入 P2 / P4。

### 6.1 自动生成知识索引 `knowledge/_index.md`（归 P2）

- 由脚本扫描各 App 卡头部**自动生成**，格式如：
  `| 包名 | versionCode | 卡片行数 | 最近验证 | 触发词 |`
  ——生成脚本需解析现行 `_template.md` 的**表格版检索索引**（`| 触发词 | 对应小节 |`），非旧平铺词列表
- **禁止手编**——索引腐烂是元数据路由的经典死穴，生成式索引根治
- 一石二鸟：同时是 §4.1 版本门禁的比对数据源，Agent 路由从"拿包名猜路径 + grep 卡片"变成确定性查表

### 6.2 App 卡头部键值区结构化（归 P2）

- 对齐场景卡已有机制（states.py 解析"触发词/判定命令"），App 卡头部统一机器可读键值区：
  `app / versionCode / 最近验证 / 触发词` —— 只限定路由必需的 3~4 个字段，**正文仍自由 Markdown**
- 延续既有设计语言，不引入新解析机制；索引生成与版本比对都变成确定性读取

### 6.3 子文档迷你路由头（归 P4）

- `docs/case-writing.md` 等 L3 长文档开头加 3~5 行"本文件路由表"（哪节解决什么问题），
  把"按需读"从文档级细化到节级；纯注释、零解析成本
- 模式已在卡片内部"检索索引"表验证有效，推广到 docs/ 而已

### 6.4 分层预算门禁（归 P4）

- `check_context_budget.py` 从只管探查缓存，扩展为分层检查：
  L1 frontmatter description ≤ N token；L2 SKILL.md ≤ N 行（配合瘦身目标 −30%）；超限 CI 报错
- 上下文纪律从散文约定变成机器检查，与本文档主线一致

### 6.5 原则红线（守住既有判断）

知识卡模板已有定论："机器靠关键词检索 + 只读命中片段，**不 parse 结构**"。本节所有改动
均不违背：结构化只用于**路由必需的最小面**（索引是生成副产品、头部仅 3~4 字段、路由头纯注释），
内容层保持"怎么写都合法"的松散性。

| 墙钟 | 总耗时、setup/步骤/收尾分段耗时 | run_case 计时戳 |
| 动作 | dump 次数、截图数/字节数、tap/输入次数 | 截图管线与动作 API 计数 |
| 等待 | sleep 合计（静态和+动态累计）、`wait_*` 等待时长 | sleep 包装器 + wait API |
| 质量 | 结果分布、自愈事件数、降级链命中层、复跑一致率 | 自愈留痕（§4.2）+ 复跑结果 |
| 守门 | 交叉 lint / check_facts ERROR 数、证据完整率（每步有截图） | lint 接入点（P0） |
| 缓存 | probes 命中率（复用 vs 重探）、版本门禁 WARN 次数 | 工作流第 2 步计数 |
| 上下文 | SKILL.md 行数、description token、被读卡片/文档行数（预算门禁值） | check_context_budget.py（6.4） |

聚合：`scripts/metrics_report.py` 从 DB 出**趋势记分卡**（Markdown，按时间列对比基线），
随报告头部输出单次记分卡。每次改框架/改规则/换模型 → 跑 golden eval → 看记分卡对比，
代替"感觉变好了"。

> **与主记录库的关系**：主记录库维持现行"同用例只留最新一条"策略不变；
> RunMetrics 写**独立表**，eval/golden 用例每次运行都追加指标行——
> 复跑一致率（M11）与墙钟趋势（M1）从 RunMetrics 取数，不受主记录库保留策略影响。
> （曾评估"DB 全留 + 产物按 script_hash 折叠"方案，2026-09-16 决定暂不采用，维持现状。）

### 7.2 量化目标表（基线 = v5 实测 178.py：311.5s / 116 dump / 110 截图 16.3MB / sleep≈110s）

| # | 目标 | 指标 | 基线 | 目标 | 采集点 |
|---|---|---|---|---|---|
| M1 | **更快** | golden 用例墙钟 | 311.5s | **≤190s** | 墙钟。推导：v5 A5.4~A5.7 省 ≈83s（ACTION_DELAY 0.3 省 26s + ensure_awake 省 15~28s + sleep 轮询化省 42s）+ M3 截图降载省 ≈35s → ≈194s，**依赖 M3 同步达成** |
| M2 | 更快 | sleep 合计 | ≈110s | **≤30s** | sleep 包装器。推导：A5.4~A5.7 合计省 ≈83s → 剩余 ≈27s，取 30s 含余量；注意 wait_* 内部 interval 也是 sleep，计入 |

| M5 | **更小** | SKILL.md 行数 | 274 | **≤190（−30%）** | 预算门禁 |

| M7 | **更智能** | 对抗 eval 通过率 | — | **≥95%** | P3 eval |
| M8 | 更智能 | probes 缓存命中率 | 未测 | 建基线后定（趋势指标） | 缓存计数 |
| M9 | **可靠** | 交叉 lint / check_facts ERROR | — | **0** | P0 守门 |
| M10 | 可靠 | 证据完整率（每步有截图+状态值） | 未测 | **100%** | run_metrics |
| M11 | **复跑稳定** | 同设备连续 5 次结论一致率 | 未测 | **≥90%**（标记为 flaky 的步骤除外）——100% 不现实：OCR 偶发 None（178 实测弹框内）、渲染竞态、网络超时是业界公认长期问题，100% 会让指标永远红 | 复跑统计 |
| M12 | 复跑稳定 | 双设备结论一致率 | 未测 | **100%**（布局变体用例除外，需在用例头声明） | P3 双设备门禁 |

> 其余目标数字的依据：M1/M2 来自 v5 时间预算表（sleep 占 35% 是下界）；M5 来自验收标准 4；
> M3 按"每步 1 张"推算；M4 按 wait_* 命中即停推算。

### 7.3 使用方式（与 P3 eval 的关系）

- P3 建 golden eval 集时**同步落打点**，首次跑出的数字即基线
- 记分卡三个触发时机：改框架后（回归）、换模型后（对比）、每周例行（趋势）
- 连续两次记分卡恶化且不可归因 → 按 SKILL.md 协作准则停下问人

> 以下为建议顺序；涉及 framework/ 的每一项实施前走变更管控提案。

## 九、验收标准（本 plan 全部落地后）

**功能验收：**

1. 换设备（手机↔平板）跑 golden 用例集，PASS 且报告中无未留痕的坐标 / 缓存值
2. 模拟 OTA（升 versionCode）后重跑：出现 WARN 提示，rid 变更被自愈链捕获并留痕
3. case 中不存在与 probes 缓存数值匹配的字面量（交叉 lint 零 ERROR）
4. SKILL.md 行数较现状下降 ≥30%，且对抗 eval 通过率不降
5. 报告可回答：哪些步骤发生自愈、哪些断言可能受版本漂移影响、FAIL 是确定性还是疑似抖动
6. `knowledge/_index.md` 与各卡头部机器一致（脚本生成，无手编漂移）；分层预算门禁在 CI 生效，超限即报错

**量化验收（对应 §7.2 目标表，M1~M12）：**

7. M1~M5 硬目标全部达标：墙钟 ≤190s（依赖 M3）、sleep ≤30s、截图 ≤6MB 且每步 ≤1 张、dump ≤2×步数、SKILL.md ≤190 行
8. M7/M9/M10/M11/M12 达标：对抗 eval ≥95%、守门零 ERROR、证据完整率 100%、同设备 5 次一致率 ≥90%（flaky 标记除外）、双设备一致
9. M6/M8 基线已建立（两周真实数据），趋势记分卡可按周输出
10. 任何一次框架/规则/模型变更，都能用记分卡回答"变好还是变坏、差多少"
