## 〇、总纲：一条主线判断

> **能力可以交给 Agent，纪律和证据不能。遇到问题及时问人，而不是自行兜底。**
>
> 判据：这条规则违反时，能否从产物（报告 / DB / 截图 / 退出码）里**机器检测**出来？
>
> | 判据类型 | 违反时产物 | 检测方式 | 归属 |
> |---|---|---|---|
> | 机制硬规则 | ERROR 拒跑 / 退出码非零 | lint / check_facts | 机制管 |
> | Agent 行为约束 | 生成质量退化 | P3b 对抗 eval | Agent 行为（P3b 机制守门） |
> | **人机通道** | **产物完全不可见**（该问没问、该报告没报告） | **差异审计**（本次 vs 上次运行对比） | **机制守门 + 人决策** |

推论：现有 SKILL.md 是"弱模型时代的防御工事"，目标形态是
**薄规则（告诉 Agent 去哪）+ 厚机制（证据 / 守门 / eval，证明它真的到了）**。

## 一、减负：把"判断"还给 Agent，把"守门"留给机制

### 1.1 可以交给 Agent 的（规则瘦身清单）

| 现在的负担 | 处置 |
|---|---|
| SKILL.md 里的事故复盘（179 / 183 教训、13 条脏记录等叙事） | 外移 `docs/lessons.md`，SKILL.md 只留蒸馏后的一句话规则 |
| explore-guide 四步 SOP 的逐步细节 | 收缩为"目标 + 约束"（到达页面且断言有据；先查缓存、禁盲猜），路径交 Agent 自选 |
| 知识卡繁重格式纪律（沉淀四问、检索索引表维护） | 降为软约定；卡里只留事实（rid / 链路 / 坑）。（注：SKILL.md:87 仍写"三问"，P4a 瘦身时一并校正） |
| lint 中维护成本高的启发式（`_PIXEL_NAME_RE`、白名单等） | 留 3~4 条最硬的（裸坐标、裸 sleep、手写轮询、偏移溯源，见 §2.3），其余靠模型判断 + 真跑失败兜底 |
| "先查复用再探查"的执行顺序 | 降级为提示 |

### 1.2 必须留在机制里的（不可下放）

1. **证据链**：每步截图、DB 入库、报告、`USER_INPUT` 追溯
2. **编造守门**（check_facts）——模型越强幻觉越隐蔽，外部校验反而越重要
3. **机械门槛**：lint 自动接入 run_case、退出码、幂等清理、版本比对
4. **复跑 / 抖动标记**（新增，见 §五）
5. **人机通道守门**（新增，见 §十）——确保 Ask 触发、归因报告、差异输出不是"可选的好意"而是"缺了就算违规"。设计原则：不是 AI 全自主，而是**遇到问题及时问人**

### 1.3 前提条件：先建 eval 再减负

规则是用真实失败"买"来的，删规则 = 假设"现在的模型不再犯此错"，**必须实验验证**：

- 建 3~5 个 golden 用例的任务级 eval（含对抗用例：诱导编造 toast 文案、诱导盲点第一个资产、诱导写死坐标）
- 最强模型跑基线 → 某规则对应的对抗用例连续通过 → 删规则；仍在犯 → 留
- 换模型 / 改规则后重跑，规则库成为"有回归测试保护的、可 GC 的资产"

> **eval 分两层，难度差一个量级**（详见 §八 P3a / P3b）：
> - **执行 eval**：跑固定脚本测框架稳定性，判定机械（PASS/FAIL），复用现有 `run_suite` + RunMetrics（§7.1）基建，成本低
> - **生成 eval**：从口述生成脚本测 Agent 行为，需先设计 eval 规范（expected-agent-behavior + 机械可判定陷阱），成本高
>
> P4 瘦身**分两档**：
> - **P4a**（复盘外移、SOP 收缩、路由头、预算门禁）——不删规则语义，只依赖 P3a 执行 eval 基线
> - **P4b**（删规则：“lint 留 3~4 条最硬的”“先查复用降级为提示”）——删的是生成行为约束，**必须依赖 P3b 对抗用例验证**（执行 eval 跑固定脚本测不出“删规则后 Agent 生成质量是否退化”）
>
> 否则会出现“执行 eval 全绿 → 放心删规则 → 生成质量退化 → 没有指标报警”的盲区。

## 二、可移植性：换设备差不是 case 写得不好，是框架没把"设备无关表达"做成默认路径

### 2.1 失败归因四类（先审计再优化）

| 失败模式 | 根源 |
|---|---|
| 坐标 / 偏移失效 | 屏幕尺寸、DPI、圆角 / 挖孔不同 |
| 元素不在首屏 | 小屏 / 换形态后布局折叠、控件进 overflow |
| 时序失败 | 慢设备渲染慢，固定 sleep / 短超时 |
| 断言失效 | 文字断言撞 ROM 字体 / 语言 / OCR 识别率 |

一次性动作：同 case 两台设备跑，diff 失败步骤并归类，拿数据定优先级。

### 2.2 框架 API 盘点与新增（治本，全部通用、符合分层边界）

> **现状核对（2026-09-16）**：wait_rid / wait_text / wait_activity 已实现
> （test_framework.py:1372/1386/1399），实施者**不要重复实现**。清单分三类：

| 类别 | API | 现状 | 说明 |
|---|---|---|---|
| **已有，无需改动** | `t.wait_rid(rid, timeout, interval)` | ✅ :1372 | P1a 的 _flow.py 改造直接消费它 |
| **已有，无需改动** | `t.wait_text(text, timeout, interval)` | ✅ :1386 | 同上 |
| **已有，无需改动** | `t.wait_activity(substr, timeout, interval)` | ✅ :1399 | 计划初稿遗漏，一并纳入 _flow.py 改造 |
| **需新增** | `t.wait_gone(target, timeout)` | ❌ | 删除类断言（"课程已消失"）的另一半 |
| **需新增** | `t.scroll_to_rid(rid, timeout)` | ❌ | 循环 swipe+dump 直到命中或出屏兜底 |
| **需新增** | `t.ocr(below=rid, above=rid)` / `region_of(rid)` | ❌ | 运行时区域派生（见 §三）。**现状**：`ocr()` 已是四参数区间签名（`y_min/y_max/x_min/x_max`，:1968），`below=`/`above=` 是加元素派生重载，不破坏现有调用，兼容成本低 |
| **需新增** | `t.block_unless(cond, reason)` / `require_* on_absent='BLOCKED'` | ❌ | 前置条件不满足时返回 BLOCKED 而非 FAIL（否则配置未命中会被记成缺陷，污染缺陷库）。**⚠️ 退出码陷阱**：`run_case.py:358-360` 的 CaseAbort 分支硬编码 `code = 1`，BLOCKED 会被写成 FAIL 退出码。修法二选一：① abort 分支改为 `code = exit_code_for(tc.final_status)`；② 引入 `CaseBlocked(CaseAbort)` 子类映射退出码 2 |
| **需评估，押后** | `t.tap_in(el, anchor=)` / `tap_right_of()` | ⚠️ | 与 `tap(rid=)`（_tap_unified:992，轮询定位+点中心）语义重叠；现有用例无"点元素非中心"的真实需求，**按 SKILL.md「升级路径」约定，等第二个 App 证明需要再做** |

```python
# P1b 新增后的目标用法（仅列新增项）：
t.wait_gone(DLG_TITLE)                    # 删除类断言
t.scroll_to_rid(ET_TEACHER)               # 小屏布局折叠
t.ocr(below=HEADER_RID, above=NAV_RID)    # OCR 区域运行时派生
t.ocr(region=t.region_of(RID_LIST))
```

**UI settled 检测：押后，拆独立 plan。** 原因：dump 全文一致性比较代价高（~300KB/次），
"稳定"定义（节点计数？bounds 不变？Activity 不变？）各有误判风险；
accessibility 事件静默需要自注册 AccessibilityService + 桥接，是独立大功能不是"配套能力"。
**当前兜底**：`wait_rid` + 短 `time.sleep`（可 lint 豁免），待 wait_* 普及后按记分卡数据决定是否立项。

### 2.3 lint 新增可移植性检查

- 手写轮询检测：`while time.time() < deadline` + `sleep` → 提示改用 `t.wait_*`
- 偏移溯源：`bounds[i] ± 字面量` 升级——同行无 `# noqa` 戳（含理由文本）即 ERROR。
  **注意**：`_flow.py` / `cases/_lib/` 下的 sleep 和偏移当前被 lint 跳过（`_` 开头排除），
  P1a 改造后 lint 须覆盖这些路径（见 §7.2 M2 口径说明）

### 2.4 定位失效四归因（写进 case-writing 一句话版）

同 APK 跨设备 rid 相同（编译进 APK），rid 找不到时按序归因：
1. **没等到**（异步渲染，dump 太早）→ `wait_rid`
2. **没滚到**（rid 在树上但 bounds 空 / 出屏）→ `scroll_to_rid`
3. **布局变体**（`sw<N>dp` 切换，rid 真不存在）→ 属 App 本来就不一样，回探查补采
4. **配置未命中**（rid 不在树上，且排除 ①②③——骨架存在但目标条目/入口整块缺失，dumpsys 版本未变）→ 检查 block_unless / require_* 条件、配置指纹（§4.1 信号 2）

断言建议"rid 断言结构 + text/状态断言语义"双确认，单个 rid 命中不代表内容对。
（厂商 App 特有注意：OTA 频繁 → 版本漂移高发，见 §四；自绘控件无 rid 是 OCR/视觉依赖的根源。）

## 三、OCR / 视觉缓存治理：缓存只许回答"找什么"，不许回答"在哪找"

### 3.1 缓存信息三去向（写进 explore-guide / case-writing 交接语义）

| 缓存内容 | 进 case？ | 形态 |
|---|---|---|
| 条件事实：rid 存在（**须运行时验证**，服务端/A/B 变更可能导致 rid 消失）、字段名、预期 toast 文案 | ✅ | 作为断言目标，运行时重取后比对 |
| 程序类：到达路径、先滚后点 | ✅ | 流程逻辑 |
| **数值类：y_min/y_max、bounds、热区偏移、OCR 区域** | ❌ **禁止** | 必须转运行时派生表达式；转不出的 → 提案 API，不许硬编码 |

### 3.2 缓存命中前验证 + 降级（对标 Midscene）

> 前置事实：**执行期使用探查缓存已被硬拦截**——v5 A1.4 已落地
> （`_guard_exec_cache` 在 cached_dump / cached_ocr 等入口抛 `ExecutionTimeCacheError`，
> probe_page 免检）。本节与 3.3 是其**进阶增强**：A1.4 管"禁止用"，本节管"怎么把提示用对"。

缓存值可当**提示**，用前运行时验证：先 dump 确认 anchor rid 存在 → 从其 bounds 推区域；
不存在 → 全屏退化。提示错了最多慢一点，不会挂。**查询 / 断言类结果永不缓存**。

### 3.3 交叉比对 lint（精确检测"缓存值回流"，进阶增强）

> 现状：现有 lint 规则 5/6/7（`_PIXEL_PARAMS` 像素参数、模块级像素常量、bounds 固定偏移）
> **已经是"字面量检测"的简化版**——本节是叠加在它之上的进阶，不是从零新建。

- 做法：case 整型字面量 × probes 落盘数值（ocr.json / meta.json / dump.xml bounds）交叉比对
- **两个待基线确定的设计参数**（实施前先跑误报评估）：容差值（±10？±50？DPI 换算？）；
  误报风险（`timeout=60` 撞上某 OCR conf 值一类）——策略：只对**模块级常量与像素参数位**做交叉
  （复用规则 5/6/7 的判据收窄），不做全 AST 字面量扫描，先量化误报率再定 ERROR/HINT 级别
- **语料时效边界**：数据源是 `storage/probes/`，而 `run_case` 启动即清理 30 分钟未访问项
  （run_case.py:309-323）→ CI（无设备）上 probes 必然不存在 → **该 lint 定位为本地探索期工具，
  不作 CI 门禁**。无语料时明确打印"未校验（probes 不存在）"，既不判通过也不判违规。
  验收 #3 同理：只能在有 probes 的真机环境判真，CI 上无法稳定验证

### 3.4 存量迁移

1. 交叉 lint 跑存量用例 **和 knowledge/*.md** → 自动得"缓存回流清单"（知识卡正文中仍残留设备实测值 + 机型戳，如 `com.zui.launcher.md:20` 的 `bounds ≈ (503,2706)-(682,2889) [TB323FU]`，同时违反 `_template.md:12` 和 §3.1；v5 A2.2 只清了卡头部，正文是漏网项）
2. 逐个替换为 `region_of` / anchor 表达式；替换不了先打 `# noqa`（含理由文本，与 v5 A2.1 删除设备戳方向一致，不另造豁免语义）留痕，进提案队列
3. 双设备 eval 放一个含 OCR/视觉断言的 golden 用例作永久门禁

## 四、版本漂移应对：版本门禁（WARN 级）+ 自愈留痕（细粒度）

### 4.1 版本门禁（1~2 小时，非 AI 参与）

- run_case 启动时 `dumpsys package <pkg>` 取 **versionCode**（整数，不用 versionName，OTA 里可能不动）
- 比对：知识卡头部"验证版本" + probes 侧版本戳——
  **⚠️ 现状矛盾**：`_template.md:24` 写 `versionName`（`1.2.3`），实际卡也是 versionName
  （如 `com.zui.calendar.md:3` 写 `9.0.0.83`），且部分卡（如 settings）根本没有该字段。
  Plan 要用 versionCode（整数），但卡里存的是 versionName（字符串），**两个量纲不可比对**。
  **P0 解法（双采）**：P0 同时采集 versionName（与现存卡比对）+ versionCode（落盘存档）；
  P2 卡头部改造完成后再切换为 versionCode 单一比对
- **隐藏前提**：run_case 启动时既无设备 serial（`--device` 可选，TestCase 内部才选设备），
  也无被测包名（需从用例路径目录名反推）。实施时须先解这两步
- **失配只打 WARN（"App 已从 X 升到 Y，缓存是 X 时期的"），不废缓存**——门禁的价值不是预测，是挂的时候消灭歧义，把"排查半天"变"一眼归因"
- 小版本升级大多数不动 rid（判断成立），真正的高发破坏是开屏广告 / 升级引导页 / 运营弹窗 / 文案微调
- **⚠️ 信号源修正**：versionCode/versionName 只能捕获 APK 替换；**运营弹窗是服务端下发、文案微调可能是 A/B 测试，都不随版本号走**。需要**双信号源**：
  - 信号 1：versionCode / versionName 变化（APK 替换）
  - 信号 2：**元素集合指纹**（dump 的 rid 集合 hash）变化（服务端变更 / A/B 切换）。**计算口径（兜底）**：按 Activity 命中 + 短 settle（wait_activity + ≤3s sleep，lint 豁免口径）后就地 dump 计算；接受一定漂移，靠“仅消失报 WARN”降噪。精确口径待 settled 检测立项后启用（见 §2.2）。只对“上次有、本次消失”的 rid 报 WARN（消失信号强），新增 rid 降 INFO（减少误报疲劳）
  - 两者任一变化 → WARN；仅信号 1 变 → 明确归因 APK；仅信号 2 变 → 归因服务端/配置，报告标"版本未变但界面已变"

### 4.2 自愈链 + 留痕（对标 Healenium）

执行时定位降级链：`rid → desc → text → 视觉`，**硬约束**：
- **只允许在同一个 dump 结果内降级**（当前 dump 里 rid 找不到 → 同一次 dump 里找 desc/text），**禁止跨 dump 重找**——跨 dump 后页面可能已变化，desc/text/视觉命中的"相似元素"身份保证已断，报告写"自愈成功"但实际可能点了错误的元素
- **降级链只用于"定位"（找到要点哪个元素），绝不参与"断言"（判断结果对不对）**；断言失败即 FAIL，不降级——否则"课程已消失"类断言会降级到长得像的另一个元素，自愈出假 PASS

- 报告单列「降级事件」，**区分两档语义**：`同 dump 降级命中`（可信度高）/ `视觉兜底命中`（须标记"元素身份未验证"，高危）
- **同一 rid 降级 ≥2 次 → 自动生成知识卡更新提案**（这是比版本比对更精确的 OTA 漂移信号）
- 厂商团队特权：变更结论可直接反馈 App 开发（外部团队做不到的闭环）
- **自愈历史记录（Locator Memory，对标 Healenium）**：降级成功后写 `healing_log.json`（per App）：
  `{activity: "EditTimetableActivity", rid: "id_save", fallback: "desc=保存", layer: "desc", count: 5, version_code: 83}`。
  **键为 `(activity, rid)` 而非仅 rid**——同 App 多页面常有同名 rid（`btn_ok` / `id_save`），仅用 rid 会串页。
  下次同一 rid 找不到时先查 healing_log → 命中则**直接走已知降级路径**（省一次 dump + 等待）。
  约束：命中后仍须用**当前 dump 验证** fallback 元素存在且合理（bounds 非空、Activity 对得上），
  验证不通过 → 丢弃该条记录、退回完整降级链（与 §3.2「缓存命中前验证」同原则）。
  版本门禁触发 WARN 时**清除该 App 全部 healing 记录**（rid 可能真变了）。
  报告新增「healing 命中率」指标，累计 count ≥3 的条目自动生成知识卡更新提案
- **终态覆盖缓冲**：知识卡更新被采纳后，自动清除该 App 下对应 rid 的 healing_log 条目（终态覆盖提示，避免双源漂移）
- **弹窗排除**：降级链 desc/text 命中时，须先排除弹窗看门狗词表中的元素（避免自愈误点权限弹窗的"保存/允许"按钮）

### 4.3 执行时管线（合成业界共识，每步）

```
1. 现采 dump（永远新鲜，学 Mobile-Agent）
```

## 九、验收标准（本 plan 全部落地后）

**功能验收：**

1. 换设备（手机↔平板）跑 golden 用例集，PASS 且报告中无未留痕的坐标 / 缓存值
2. 模拟 OTA（升 versionCode）后重跑：出现 WARN 提示，rid 变更被自愈链捕获并留痕
3. case 中不存在与 probes 缓存数值匹配的字面量（交叉 lint 零 ERROR）
4. SKILL.md 行数较现状下降 ≥30%（**注意：P4a 仅结构整理，~274→190 的 −84 行缺口只能由 P4b 补**；纯叙事仅 ~10 行量级），且对抗 eval 通过率不降
5. 报告可回答：哪些步骤发生自愈、哪些断言可能受版本漂移影响、FAIL 是确定性还是疑似抖动
6. `knowledge/_index.md` 与各卡头部机器一致（脚本生成，无手编漂移；**本地 setup / 探查后校验**，CI 不校验其内容，见 §6.2）；分层预算门禁在 CI 生效，超限即报错
7. **P3b eval 规范经人确认**：expected-agent-behavior 文档落地 + 至少 1 个对抗用例端到端跑通（陷阱结果可机械判定）
8. **P3a 双设备门禁自动化**：脚本能自动发现 ≥2 台在线设备并串行跑 golden eval，人工介入仅限设备物理故障
9. **人机通道生效**：探查期 Ask 触发有记录且答案落卡；执行期报告含"本次与历史的差异"节（自愈事件、元素集合指纹变化、配置变更）。**构造验收方式**：故意写一个引用无出处文案的断言 → 应触发 Ask 并落卡（可重复验证，不依赖"碰巧发生过"）
10. **反馈环达标**：`DSH_SKIP_IF_READY=1` 已生效（goto_* 前置链路跳过，设备已就位时显著缩短；② 代码已实现于 `_flow.py`，本项验收 = 真机跑一次确认跳过生效）；probes 清理阈值可通过环境变量 `DSH_PROBES_MAXIDLE_MIN` 配置（含 0=关闭）；**M13 反馈环墙钟已采集**（基线值在 P0b/P1a 落地后首次 golden eval 时确定）

**量化验收（对应 §7.2 目标表，M1~M13）：**

11. **M2~M4 硬目标达标**：sleep ≤30s（lint 静态求和）、截图 ≤6MB 且每步 ≤1 张、dump ≤2×步数；**M1（≤190s）、M5（≤190 行）为条件目标**——分别依赖 v5 A5.4/A5.6/A5.7 落地与 P3b→P4b 落地，各自前提未达成前不计入硬验收
12. M7/M9/M10/M11/M12 达标：对抗 eval ≥95%、守门零 ERROR、可截图步骤证据完整率 100%、同设备 5 次一致率 ≥90%（flaky 标记 + **配置差异**除外）、双设备一致率 ≥90%（flaky 标记步骤 + 布局变体 + 配置差异除外）。**"配置差异"除外判据**：必须同时满足 §4.1 **信号 2 变化 + 信号 1 未变** + 脚本 hash 未变，否则不算除外——OTA 会同时改变两个信号，缺"信号 1 未变"会让版本漂移被误判为配置差异、绕过版本门禁（避免变成万能免责条款）
13. M8 基线已建立（≥3 次运行 median ± std，两周真实数据），趋势记分卡可按周输出；M6 为观察项（待 Agent 侧埋点后采集）
14. 任何一次框架/规则/模型变更，都能用记分卡回答"变好还是变坏、差多少"

## 十、人机通道：不是 AI 全自主，是遇到问题及时问人

> **设计原则**：机制负责发现问题并及时问人，人做决策。AI 不需要“智能地兜底”，而是“明确地报告 + 等待指示”。

### 10.1 探查期阻塞式 Ask

> **执行主体分层**：§10.1 的“阻塞并问人”涉及两层协作——
> - **机制侧**：probe_page 检测“无进展差集”、block_unless 返回 BLOCKED → 报告节 + RunMetrics 留痕
> - **Agent 侧**：SKILL.md 协作准则加一条“见 §10.1 信号必 Ask 并阻塞等人”（P4a 蒸馏时同步）
>
> **⚠️ 实施前提**：探查期差集对比跨子进程（每次 probe_page 是独立 run_case 调用），状态须持久化到 RunMetrics（probes 目录 30 分钟即清，跨会话不可靠，见 §7.1），否则下次子进程拿不到历史差集数据。

Agent 探索阶段遇到以下信号时**阻塞并问人**（而非自行猜测/跳过）。每条触发前都有**自解优先窗口**（与 explore-guide.md 口径一致）：Agent 先按现有口径自主补采（单步 10 秒探针 / 2 次重试），仍无解才 Ask：

| 触发信号 | 自解优先窗口 | 含义 | 动作 |
|---|---|---|---|
| rid 找不到 + 无 fallback 匹配 | 先补采当前页（可能没采到） | 知识不足，无法继续 | 补采后仍无解 → 阻塞 + Ask |
| 无进展差集（连续两次 probe_page 的 rids/texts 差集为空） | 可算口径，无需补采 | Agent 在原地打转 | 阻塞 + Ask |
| 配置条件不满足（block_unless / require_* 返回 BLOCKED） | 检查是否有替代路径 | 前置条件缺失 | 无替代 → 阻塞 + Ask |

**Ask 频率红线**：每用例 Ask >2 次要复核阈值设定（避免"事事请示"）。
**Ask 留痕载体**：报告节 + RunMetrics 表（§7.1 人机通道维度）。
答案直接落知识卡（或配置），下次不再问同一个问题。

### 10.2 执行期非阻塞归因

跑用例时**不暂停**，但报告里必须输出「本次与历史的差异」节：

- **自愈事件**：哪些步骤走了降级链、降级层是什么
- **元素集合指纹变化**：dump 的 rid 集合与上次运行的 diff——定义见 §4.1 信号 2（含兜底计算口径：Activity 命中 + 短 settle），基线存储见 §7.1 RunMetrics 约束。**等级区分**：上次有、本次消失的 rid → WARN（消失信号强）；新增 rid → INFO（减少误报疲劳）
- **配置变更**：block_unless / require_* 条件变化、元素集合指纹变化（即“配置指纹”，与信号 2 合一，见 §7.1 存储粒度说明）
- **变更归因决策表**（每个 FAIL/BLOCKED 步骤附归因分类，不是 §2.4 的定位归因）。**判定按表序执行，先命中先归因**——多信号可同时命中（如脚本与版本同变）；“复跑不一致”“换设备”仅在脚本与版本均未变时参与判定：

| 信号 | 归因 |
|---|---|
| 无基线（首次运行） | 跳过对比，不标未归因 |
| 脚本 hash 变 | 脚本类（改了用例导致） |
| versionCode/versionName 变 | APK 类（版本漂移） |
| 元素集合变（版本/脚本未变） | 配置类（服务端/A/B） |
| 复跑不一致 | 抖动 |
| 换设备 | 布局变体 |
| 以上均未命中 | 未归因（交人） |

### 10.3 配置下发

> **范围声明**：本节拆两层——
> - **MVP 归 P1b**：block_unless / require_* BLOCKED 变体 + 退出码修复（§2.2）+ 配置指纹记录落 RunMetrics
> - **完整配置层归 P6 / 独立 plan**：骨架 vs 配置内容分离 DSL、热更新、profile 管理——本质是数据驱动用例框架，是独立立项量级，不应塞进已超载的 P1
>
> 放在 §十 下是因为它与人机通道强耦合（配置未命中 → Ask）。

- **MVP（P1b）**：block_unless / require_* 的 BLOCKED 变体——前置条件不满足时返回 BLOCKED 而非 ERROR，报告里明确标注“配置条件 X 不满足”
- **配置驱动断言**（替代原“双态断言”）：用例按当前配置指纹选择期望态（配置 A → 期望存在；配置 B → 期望不存在），断言恒为单态严格——与 §4.2“断言不降级”硬约束一致。配置指纹不在枚举内 → BLOCKED + Ask（接 §10.1）。正确应对是“让期望跟着配置走”，不是“放弃判定”
- **配置指纹**（= 元素集合指纹，见 §7.1 存储粒度说明）：每次运行记录当前 dump 的 rid 集合 + 其 hash，与上次对比 → 报告输出“新增 / 消失的 rid”明细 diff（§10.2）
- **完整配置层（P6）**：骨架 vs 配置内容分层——用例骨架（步骤序列 + 断言目标）与配置（具体 rid / 超时值 / 条件表达式）分离，配置可独立更新。实施归 P6 / 独立 plan
