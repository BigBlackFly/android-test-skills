## 一句话结论

探索慢的根因**不是缺方法论**，而是**已有方法论从未被执行**——
`storage/probes/` 与 `storage/traces/` 在这次讨论前**从未存在过**。
所以改动方向是**把已有机制接进默认路径**，而不是再造一套。

## 起因：一句抱怨引出的量化

用户最初的抱怨是「一个用例探索为啥 20 分钟」。

查 `D:\dsh\` 下遗留的临时探针脚本，时间线如下：

```
18:00  probe183.ps1   ┐
18:03  probe183b.ps1  │
18:05  probe183c.ps1  │
18:06  probe183d.ps1  ├─ 9 个连续脚本 = "点一步看一步"的物证
18:07  probe183e.ps1  │   （18:00 → 18:25，25 分钟）
18:08  probe183f.ps1  │
18:17  probe183g.ps1  │
18:22  probe183h.ps1  │
18:25  probe183i.ps1  ┘
19:34  probe_back.ps1     ← 探返回路径（列表页 BACK 的边）
19:42  probe_edit.ps1     ← 探编辑页
19:52  probe_weeks.ps1    ← 探字段滚动（**误判**，白耗）
20:01  probe_ime.ps1      ← 探 IME 吞 BACK
20:06  probe_rankb.ps1    ← 验证排序方案
20:08  probe_ranknew.ps1  ┘
                         跨度 127.5 分钟
```

**关键**：前 9 个脚本若第一次就用 `probe_page` 一次性拿全 dump，就是 1 次调用。
"点一步看一步"不是效率问题，是**把 1 次操作拆成 9 次**。

15 个脚本中**至少 11 个本可离线完成**——它们的存在本身就证明了落盘缺失。

## 根因（讨论确认：A + B）

- **A（纪律）**：SOP 写成链接，不构成约束。且旧工作流把第 3、4 步
  （查 `probes` 缓存 / 用 `probe_page` 采集）措辞为"都没有，**才**用"，
  读起来像前两步失败后的**补救**；实际它是新链路的**主路径**。
- **B（结构性诱因）**：`_flow.py` 厚流程复用越顺，越容易跳过探查——
  拿到能跑的入口就觉得"剩下随便试"。
  **复用解决"到达"，采集解决"到达后有什么"，两者不可替代。**

## 探查模型（讨论定稿）

```
① 查知识卡 + 已有用例/代码 → 确定"已知边界"：能到哪一步
     · 边界是一个**具体页面坐标**，不是一个范围
       例：「已知可以导航到【课程列表界面】了，列表界面之后的动作没有记录」
           → 边界 = 课程列表界面，从它之后开始探
     · 知识卡与已有用例**两者都看，取更远的那个**
     · 不明确时**多次查询**；查完仍无 → 找人要
       （找人时讲清：查了什么、查到哪、缺什么 —— 不要空手问）
② 验证边界可达（到不了 = 知识卡有错，先修）
③ 从边界开始探查，**只探最后一步**（用例真正要断言的页面）
     每步落盘：动作记录 + 当时页面 dump
④ 看着 dump 反查验证点（找 rid / text）——相信 AI 的判断
     查不到 → 优先认为采集不完整，回去补采；而不是判定"元素不存在"
⑤ 合成用例 → 真机终验**一次**
⑥ 清理（自动，见下）
```

## 设计原则：机制管"记性"，AI 管"判断"

**充分相信 AI 的能力。** AI 看着 XML 找按钮、判断下一步怎么走是成熟能力，
不需要规则绑住。机制只做 **AI 确实做不到的事——记住**：

| 机制该做（AI 会忘的） | 机制不该做（AI 自己能判断的） |
|---|---|
| 把 dump 拿到并落盘 | 替 AI 判断"这是哪一页" |
| 每步自动记录 | 替 AI 决定"该不该采" |
| 超时自动清理 | 强制自检清单、检查点 |
| 完整保留原始数据 | 预先提炼成固定格式（会丢细节） |

**这条原则来自一次自我纠正**：本文初稿写了"四种情况分流表""页面指纹方案"
等一堆规则，是把 AI 本来就能做的判断写成了表格。**规则表写太细，
会让 AI 只会照表办事。**

## 关键决策及其理由

### 决策 1：卡住才找人（不是"出问题就找"）

| 卡住类型 | 处理 | 理由 |
|---|---|---|
| **找不到**（定位失败） | AI 先自行补采 → 仍不行才找人 | AI 有自愈路径 |
| **预期不符**（路径对但结果不对） | **直接找人** | AI 无解：不知道是应用错了还是自己错了 |

重试口径：**单步探针**（10 秒级）、**2 次**、**当场中断**。
理由：整跑一轮 2-4 分钟，"3 次"就是 10 分钟——正是被抱怨的模式。
同一动作 2 次结果**一致**的不符预期 = 可复现 = 报 bug 的黄金证据。

### 决策 2：清理按"最后访问"而非"创建时间"

**加时间戳，超过 30 分钟自动删除，由代码执行。**

- 183 从探查到验证通过跨了 2 小时（18:00 → 20:08）。若按创建时间 30 分钟，
  **写代码写到一半缓存就没了**，反而逼着重跑真机——正是要避免的。
- 按最后访问（mtime）能自动区分"还在用"和"忘了"。

### 决策 3：由代码删，不靠 AI 删

若落盘靠 AI 自觉、删除也靠 AI 自觉，就是**一个自觉弥补另一个自觉**。
物证：讨论当天 `D:\dsh` 下 15 个临时探针脚本**全部未清理**。

### 决策 4：错误路径也保留（不主动删）

AI 判断"这是错的"本身可能出错。183 里我三次**确信走对**实际都错
（以为到周视图、以为字段要滚动、以为候选1是课程表）；发现时 dump 已丢失，
只能重跑真机。所以**一律保留，靠超时自动清**，不做对错判断。

### 决策 5：页面指纹搁置

单 Activity + 多 Fragment 的 App（Compose / Flutter / H5 同理）
`current_activity()` 永远返回同一个值，多页会被当成同一页。

曾考虑用**内容指纹**（`包名 + Activity + 关键 rid 集合哈希`）解决，**决定先搁置**：

- 不是瓶颈——瓶颈是"没落盘"，不是"落盘没去重"
- 页面标识用人工 label 已够用
- 指纹抖动（时间/未读数/列表顺序）需实测才能定阈值，现在做是猜

**等跑过几个真实用例再决定。**

## 落地清单（2026-09-10）

**过程中最重要的一次发现**：原计划"实现落盘机制"，做的时候发现
**框架里早就有了**——`_dump()` 已挂 `trace.snapshot()`，`TraceRecorder`
已实现 `snapshot` / `event` / `index.json` / `_prune_old_sessions`。

**唯一真正缺的是"按时间的清理"，以及"机制从未被启用"。**
所以实现重点改为**把已有机制接进默认路径**，而不是造新轮子。

| 改动 | 文件 | 内容 |
|---|---|---|
| `probe_page` 自动开 trace | `framework/test_framework.py` | 调用即视为探查模式，自动 `set_trace()`；此前要求调用方"记得调"，故从未启用 |
| meta.json 加时间戳 | 同上 | 新增 `accessed`（最后访问，清理基准）与 `created`（首次采集） |
| `cleanup_probes()` | 同上 | 按 `accessed` 超 30 分钟删除；老缓存无该字段则退回 mtime |
| `list_probes()` | 同上 | 列出缓存与空闲时长 |
| 按空闲时间清理 | `framework/trace_recorder.py` | `max_idle_min`（默认 30，可用 `DSH_TRACE_MAXIDLE_MAX` 调） |
| 启动时清理 + 提示 | `framework/run_case.py` | 每次跑用例自动执行，并打印现存缓存 |
| 规则写入 AI 文档 | `SKILL.md` / `docs/explore-guide.md` | 第 3、4 步定位修正；"卡住才找人"；清理说明 |

**验证**：

- 离线自测清理逻辑：60 分钟前（有 accessed）删 ✅、90 分钟前（老格式靠 mtime）删 ✅、5 分钟前保留 ✅
- 真机验证 `probe_page` 自动开 trace：`enabled False → True`，落盘 4 份 xml + `index.json`
  （`src` 字段记录每份 dump 的来源调用点）✅
- **183 回归：PASS 20/20，无退化** ✅

4. **页面指纹是否需要**——跑过几个真实用例后再评估（见决策 5）。
5. **效果验证**——用下一个新用例实际测一次，看探索耗时是否真的下降。
